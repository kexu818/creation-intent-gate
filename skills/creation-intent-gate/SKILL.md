# 创造意图门

把“我想做一个东西”的功能冲动，转化为自洽、他洽、可碰撞现实的创造物意图。先提高意图质量，再利用 AI 的执行速度。

## 核心契约

1. 先读当前工作区、已有 MVV、项目状态和相关材料，再提问。
2. 把 Mission 和最终 Values 留给人判断；让 AI 负责展开 Vision、搜集证据、生成样本和压缩信息。
3. 不把页面、Agent、自动化、粉丝数、收入数字或功能名称直接当作 Mission；它们可以是合法的执行目标。已有 Mission 和范围时，不反复质疑明确功能。
4. 不停留在漂亮的战略文档。完成收敛后，锁定一个 1-3 天可碰撞现实的最小创造物。
5. 用户说“先讨论”时只讨论，不写文件或进入构建。只有当前对话已经确认 Mission 和主 Vision 后，“干”“开始做”才代表通过完整门；初始请求里的“现在就做”不能绕过它。
6. 不把评分、象限坐标或市场定位包装成客观事实；标注证据、推断和不确定性。
7. 用户明确说“跳过创造意图门”或 `skip creation intent gate` 时，简短确认已跳过并继续执行。跳过只作用于本 skill 的 Mission、Vision、Values、收敛和碰撞步骤，不构成对任何文件修改、删除、付款、合同、隐私、凭证、外部调用或公开承诺的授权；这些动作仍按原请求和原有安全确认处理。

## 选择运行深度

启动时先以当前 `SKILL.md` 所在目录为根，检查 `references/method.md`、`references/convergence.md`、`assets/mvv-decision-template.md` 和 `assets/reality-collision-card.md` 是否可读。任一缺失或不可读时明确报告具体路径；不得静默跳过对应方法，也不得声称已完成完整门。只在用户同意降级后，使用本文件中的最低契约继续。

### 轻量门

用于可逆、单人、一天内完成、不涉及客户承诺、金钱、隐私或长期维护的创造物。

完成四件事后继续执行：

1. 写出一句 Mission。
2. 展开 3 个明显不同的 Vision。
3. 选 1 个并说明放弃另外 2 个的理由。
4. 定义一个最小现实碰撞和一条原预测。

不要让轻量门变成新的拖延。

轻量门在一个简短回复内完成：最多 4 个短项目和一句选择结论，默认不超过 350 个汉字，不另起多轮确认。存在会改变结果的高影响歧义时，只问一个问题。

### 完整门

用于客户项目、产品、服务、业务、长期系统、自动化、组织设计、公开内容体系，或任何涉及多人、金钱、数据、权限、外部承诺和持续维护的创造物。命中明确风险条件时，说明触发理由后直接使用完整门；只是因信息不足而无法在轻量门与完整门之间判断时，先说明分级依据并问用户一个确认问题，不静默升级。

Mission 与主 Vision 未经用户确认前，不进入详细 plan 或 build。已有经过确认的 MVV 时，读取并复述关键约束后直接进入后续阶段。

完整门的硬性通过条件：

- Mission 是用户确认的状态转化，不是 AI 自己填好的产品描述。
- 默认展开 5 个、最少 3 个、最多 8 个真正不同的运行画面；路径已实质穷尽时停止并说明，一句泛化 Vision 不算完成。
- 已用自洽、他洽和代价完成选择；“真实、透明、简单、用户优先”等通用好词不算 Values。
- 已选定主 Vision、备选 Vision和暂停项。
- 已定义现实对象、原预测和 1-3 天最小碰撞。

任一条件未满足时，不列完整功能清单，不给出“按建议做即可开工”，也不把草案表述成最终 MVV。

## 完整工作流

### 1. 建立 Context

- 读取项目入口、状态文档、历史决策、用户原话和已有创造物。
- 区分可查证事实、用户选择、AI 推断和外部假设。
- 指出当前的“功能冲动”：用户表面上想造什么。
- 只询问无法从环境获得、且会改变方向的高杠杆问题。一次优先问一个。
- 没有可用 Context 时，先问一个真实场景问题或提出 Mission 草案请用户校准；不要替用户一次性编完 Mission、Vision 和 Values。

### 2. 锁定 Mission

使用这个句式：

> 帮助【具体对象】，把【可观察的当前状态】，转化为【可观察的目标状态】，同时不牺牲【关键边界】。

检验 Mission：

- 去掉当前产品或工具名称后仍然成立。
- 描述的是对象的状态转化，不是创作者的欲望。
- 目标状态可以被现实观察，而不是抽象好词。
- 边界说明不想通过什么代价获得结果。

Mission 已清楚并由用户确认时明确说“Mission 已锁定”，不要为了流程继续改写。AI 初次提出的 Mission 必须标记为草案。

### 3. 展开 Vision

完整门默认展开 5 个成功画面，允许 3-8 个。每个 Vision 必须描述“运行起来后的世界”，而不是功能清单。只写“客户看得懂、调整可追溯”这类产品效果，不构成多个 Vision。当新的候选只是在更换名称或界面时，停止扩展并说明路径已经穷尽。

从相关维度制造真正不同的路径：

- 用户最终体验与关系形态。
- 价值产生机制与替换旧体验的方式。
- 人、Agent、脚本和第三方工具的分工。
- 事实源、反馈、学习和复利资产。
- 服务、产品、基础设施、网络或生态等不同形态。
- 保守低替换成本路径与高杠杆路径。

不要强迫不相关的维度凑数。给每个 Vision 一个可记忆的名称、一幅终局画面、核心代价和最大未知。

### 4. 把 Vision 画出来

当 Vision 超过 3 个或用户表达阅读困难时，必须生成实际可查看的视觉产物：PNG、SVG、渲染后的 HTML 截图或其他当前界面能直接显示的图片。

画图前先做一次能力探测：确认至少有一条可用生成路径和一条可用查看路径。生成路径可以是本 skill 的 Python 脚本、已有可视化工具或 HTML 渲染；查看路径可以是本地图片查看工具或浏览器截图。两条路径无法同时成立时先报告限制，不启动不可验收的画图任务。

- 不把 Mermaid、Graphviz、SVG 或绘图库源码当作图片交付。
- 每张图只服务一个判断；附一句“这张图怎么看”。
- 视觉生成后使用本地图片查看工具实际打开，检查文字、重叠、裁切和可读性；SVG 先在浏览器打开或转成 PNG 后检查。通过标准是：标题与标签完整可见、标签之间无明显遮挡、关键文字在交付显示尺寸下无需放大即可读；任一不满足就调整后重验。
- 需要界面想象时画真实界面草图；需要选择时画路径图或定位图，不混用。
- 优先使用当前环境已有的可视化或图片工具。运行 PNG 脚本前检查 Pillow 和中文字体；任一缺失时由同一脚本自动输出 SVG，仍需实际打开验证。查看工具不可用时至少验证文件存在、非空、格式和尺寸正确，并标记“未完成视觉检查”，不得把图称为已验收。无法生成任何图片时明确说明限制，再用结构化文字继续，不得伪称已交付图片。

### 5. 用自洽与他洽收敛

读取 [references/convergence.md](references/convergence.md)。skill 内所有相对链接都以当前 `SKILL.md` 所在目录为根解析，不以用户项目的工作目录解析；模板只读取，不在安装目录内改写。

- 自洽用于判断这个画面是否符合用户的兴趣、能量、能力、身份、掌控感和长期复利方向。
- 他洽用于判断目标对象是否存在真实痛点、使用/配合/付费意愿，以及新体验能否覆盖替换成本。
- AI 先基于 Context 提议评分和证据，用户拥有最终修改权。
- 商业或客户创造物在最终收敛前核验市场；优先一手来源，必要时并行调研。
- 输出一个主 Vision、一个备选 Vision、明确暂停/放弃项及理由。
- 把 Values 写成选择规则和禁区，不写口号。
- 没有用户 Context 支撑时，不替用户断言什么与其自洽；先展示待校准判断。

需要二维图时，使用 `scripts/render_convergence_map.py` 生成真实 PNG；依赖缺失时接受脚本返回的 SVG。两种格式都必须检查成图。

### 6. 设计现实碰撞

使用现实碰撞原则：

> 用户价值 = 新体验与旧体验之差 - 替换成本

依次写清：

1. 目标对象现在如何解决问题。
2. 新体验究竟改善了什么。
3. 对方为了采用它要付出什么替换成本。
4. 当前真正限制系统的最大卡点是什么，而不是最容易完成的任务是什么。
5. 1-3 天内可以 build 的最小创造物是什么。
6. 要拿给哪个真实的人、客户或流程使用。
7. 原预测、成功/失败信号和预期获得的新信息是什么。

使用 [assets/reality-collision-card.md](assets/reality-collision-card.md) 作为模板。收敛未确认前只在聊天中填写；确认落盘后保存为决策稿相邻的 `assets/<创造物-slug>/reality-collision-YYYY-MM-DD.md`，不得写回 skill 安装目录。

### 7. 设计端到端回路

读取 [references/method.md](references/method.md) 中的“端到端回路”部分。

标出：输入、确定性处理、Agent 判断、人的质量门、输出、证据、反馈、记忆和下一轮更新。能够脚本化的确定性步骤不要交给大模型。

判断当前处于八层回路中的哪一层，并只定义下一层所需的最小升级。不要因为画出了完整架构就声称已经自适应。

### 8. 固化并进入 Build

用户确认后：

- 先确定唯一项目根目录：优先使用用户明确给出的目录；否则使用 Codex 当前任务公开的 workspace root；两者都没有时，才从当前任务工作目录向上选择最近的项目标记目录（如 `10_方案与执行/`、项目状态文件、`AGENTS.md`、`CLAUDE.md`、`.git` 或 `README.md`）。同一目录命中多个标记仍算一个候选，不按标记类型跳到更高层。
- 不自动选择用户主目录、`/tmp`、全局 skill 安装目录或仅作为容器的 Vault 根目录。多个根目录都合理、候选只是宽泛容器或没有可写根目录时，不猜路径、不落盘；保留聊天产物并询问一次保存位置。
- 项目存在 `10_方案与执行/` 时，将决策稿保存到该目录；否则保存到项目根目录。文件名使用 `YYYY-MM-DD-<创造物>-MVV决策稿.md`。写入前检查同名文件；已存在时依次使用 `-v2`、`-v3` 等首个未占用名称，并在回复中报告实际路径，绝不覆盖旧稿。
- 使用 [assets/mvv-decision-template.md](assets/mvv-decision-template.md) 生成决策稿。
- 将 Vision 图、收敛图、碰撞记录和必要的回路图保存到决策稿相邻的 `assets/<创造物-slug>/`。不得把用户产物写进全局 skill 安装目录。
- 写文件前先向用户报告将要使用的绝对目标路径。
- 保留原始版本；现实反馈到来后追加新一轮碰撞，不悄悄重写旧预测。
- 再生成实施 brief：当前最大卡点、V1 范围、明确不做、验收信号和第一步。

## 人机责任边界

AI 负责：读取 Context、展开 Vision、研究市场、生成视觉样本、提出评分、压缩差异、设计实验、整理记录。

人负责：确认 Mission、判断 Values、选择代价、承担对外承诺、决定是否发布或进入 Build。

将高风险确认放在回路末端并不等于“人在回路中”。付款、合同、隐私、客户承诺、公开发布等事项必须保留人的质量门。

## 失败模式

- 用户一说“做页面”就讨论框架和按钮。
- 用同一条路径换皮凑出多个 Vision。
- 只给一个泛化 Vision 就宣布完成 MVV。
- 把自洽评分当成替用户表达内心。
- 用“真实、透明、简单、客户优先”等普适好词冒充 Values。
- 没有外部证据却给他洽打高分。
- 在用户尚未确认 Mission 和主 Vision 时，用一句“按建议做”跳进功能范围。
- 为了完整走流程而忽略已经确认的决策。
- 无限讨论，没有最小创造物和现实对象。
- 只在聊天里完成收敛，未在确认后保存到项目 Context。
- 交付图表源码、模糊草图或不可读图片。
